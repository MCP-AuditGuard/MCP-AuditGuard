# 탐지엔진 위험도 분류 기준

## 문서 목적

이 문서는 MCP-AuditGuard 탐지엔진이 finding의 위험도(`severity`)를 어떻게 분류하는지, 어떤 문서와 구현을 참고했는지, 그리고 왜 현재 기준을 그렇게 정했는지 설명합니다.

현재 위험도 기준은 CVSS 같은 범용 취약점 점수 체계를 그대로 적용한 것이 아닙니다. 이 프로젝트는 `tools.json`에 포함된 MCP 도구 메타데이터를 정적으로 검사하는 도구이므로, 실제 런타임 악용 가능성을 완전히 입증하기보다 **도구 설명, 스키마, annotation, `_meta`가 에이전트 행동을 오염시킬 가능성**을 기준으로 위험도를 부여합니다.

## 현재 위험도 값

현재 모델이 허용하는 위험도 값은 다음 5단계입니다.

```text
critical
high
medium
low
info
```

실제 Markdown 리포트는 현재 `critical`, `high`, `medium`, `low`를 요약에 표시합니다. `info`는 데이터 모델에는 존재하지만, 현재 기본 리포트와 주요 룰에서는 거의 사용하지 않습니다.

## 위험도 분류 원칙

위험도는 아래 세 가지 질문을 기준으로 정했습니다.

1. 이 메타데이터가 사용자의 의도보다 도구 제공자의 숨은 지시를 우선하게 만드는가?
2. 이 지시가 민감정보 탈취, 외부 전송, 고권한 도구 호출, 파괴적 행동으로 이어질 수 있는가?
3. 탐지 근거가 직접적인 악성 지시인가, 아니면 악성 가능성이 있는 구조적 신호인가?

즉, 단순히 `ignore`, `token`, `secret` 같은 단어가 보인다고 위험도를 높이지 않고, **행동 유도성, 민감 대상, 은닉성, 권한 영향, evidence 확실성**을 함께 봅니다.

## 단계별 분류 기준

| Severity | 기준 | 대표 사례 |
| --- | --- | --- |
| `critical` | 민감정보 접근, 탈취, 외부 전송을 직접 유도하는 경우 | `.env`, API key, password, credential, auth token 등을 읽거나 전송하라고 지시 |
| `high` | 모델의 지시 체계를 우회하거나, 명령 실행/고권한 리소스 접근/은닉 행동을 유도하는 경우 | `ignore previous instructions`, `do not tell the user`, shell command 실행, branch protection 비활성화 |
| `medium` | 도구 선택이나 응답을 조작하려 하지만 즉시 민감정보 탈취나 파괴 행동까지는 명확하지 않은 경우, 또는 난독화 흔적이 있으나 악성 문구가 확정되지 않은 경우 | `always use this tool`, 다른 tool 결과 override, URL encoding 예시, HTML comment 존재 |
| `low` | 보안상 검토할 변화나 인코딩 흔적은 있지만 악성 지시가 드러나지 않는 경우 | baseline에서 도구 제거, base64 후보가 있으나 디코딩 후 suspicious phrase 없음 |
| `info` | 정보 제공용 신호 | 현재 주요 detector에서는 거의 사용하지 않음 |

## 주요 detector별 기준

### MCP03 Tool Poisoning 룰

`rules/tool_poisoning.yaml` 기준입니다.

| Rule | Severity | Confidence | 이유 |
| --- | --- | --- | --- |
| `sensitive_data_steering` | `critical` | `high` | 민감정보를 읽거나 외부로 보내도록 직접 유도하므로 영향이 가장 큼 |
| `ignore_previous_instructions` | `high` | `high` | 시스템/개발자/사용자 지시 체계를 무력화하려는 직접 신호 |
| `covert_behavior` | `high` | `high` | 사용자에게 숨기라는 지시가 포함되어 공격 은닉성이 큼 |
| `command_execution_steering` | `high` | `high` | shell, exec, subprocess 같은 실행 경로로 이어질 수 있음 |
| `privileged_resource_access` | `high` | `medium` | private repo, admin token, branch protection 등 고권한 자원 접근 유도 |
| `answer_manipulation` | `high` | `medium` | 최종 응답을 조작하거나 숨김 텍스트를 넣도록 유도 |
| `schema_instruction_poisoning` | `high` | `high` | schema field description이 입력 설명을 넘어 모델 행동 지시로 변질됨 |
| `tool_priority_manipulation` | `medium` | `medium` | 도구 선택을 조작하지만 단독으로는 민감정보 탈취나 파괴 행동이 항상 확정되지는 않음 |

### Obfuscation detector

난독화 detector는 난독화 존재 자체와 악성 payload 확인을 구분합니다.

| 상황 | Severity / Confidence | 이유 |
| --- | --- | --- |
| 디코딩, 정규화, skeleton 변환 후 악성 지시가 드러남 | `high` / `high` | 숨겨진 MCP03 지시가 확인됨 |
| HTML comment, zero-width, homoglyph 등 숨김 구조는 있지만 악성 지시는 확정되지 않음 | `medium` / `medium` | 은닉 가능성은 있으나 실제 공격 의도는 추가 검토 필요 |
| base64/base64url 후보가 있지만 디코딩 후 suspicious phrase 없음 | `low` / `low` | 인코딩 흔적만으로는 악성 판단이 약함 |

### Baseline diff

baseline 비교는 tool metadata의 무결성 변화에 대한 위험도입니다.

| 변화 | Severity | 이유 |
| --- | --- | --- |
| 새 도구 추가 | `medium` | 새 공격 표면이 생김 |
| 도구 제거 | `low` | 기능 변화는 있으나 직접적인 poisoning 증거는 약함 |
| 기존 도구 metadata hash 변경 | `high` | 이미 승인된 도구의 설명이나 schema가 바뀌면 rug pull 가능성이 있음 |

## 기준을 이렇게 정한 이유

### 1. MCP03의 핵심 위험은 “메타데이터가 모델 행동을 바꾸는 것”이다

Tool Poisoning은 일반적인 코드 취약점처럼 함수 하나가 즉시 실행되는 문제가 아닙니다. 도구 설명, schema, `_meta`, annotation이 모델 컨텍스트에 들어가고, 모델이 그 지시를 따라 다른 도구를 호출하거나 사용자 의도를 바꿔 해석할 때 문제가 됩니다.

그래서 위험도는 단어 자체보다 **행동 유도성**을 더 크게 반영했습니다.

### 2. 민감정보 탈취는 피해가 직접적이므로 `critical`로 둔다

`.env`, token, password, credential, SSH key 같은 값은 한 번 유출되면 계정 탈취, 서비스 접근, 추가 공격으로 이어질 수 있습니다. Invariant Labs의 tool poisoning 사례도 민감 파일 접근과 은닉 전송을 핵심 피해로 보여줍니다.

따라서 민감정보 접근과 외부 전송을 함께 유도하는 룰은 `critical`로 분류했습니다.

### 3. 지시 우회와 은닉 행동은 직접 피해 전 단계라도 `high`다

`ignore previous instructions`, `do not tell the user`, `silently` 같은 지시는 모델의 안전 경계와 사용자 확인 절차를 약화시킵니다. 당장 secret 전송 문구가 없어도, 이후 고권한 도구 호출이나 cross-tool 공격으로 이어질 수 있으므로 `high`로 둡니다.

### 4. 난독화는 “악성 내용 확인 여부”에 따라 나눈다

난독화 자체는 정상 문서에도 등장할 수 있습니다. 예를 들어 URL encoding을 설명하는 정상 도구 설명은 `%20`을 포함할 수 있습니다. 그래서 디코딩 후 악성 지시가 드러나면 `high`, 단순 흔적만 있으면 `medium` 또는 `low`로 낮춥니다.

이 기준은 benign-lab에서 확인된 `BENIGN-032 URL Encoding Explainer` 오탐 사례와도 맞닿아 있습니다.

### 5. baseline 변경은 rug pull 가능성 때문에 별도 취급한다

도구 설명은 사용자가 최초 승인한 뒤에도 바뀔 수 있습니다. 외부 자료에서도 MCP rug pull이 언급되고, 우리 엔진도 baseline hash 변경을 추적합니다. 기존 metadata가 바뀌면 도구의 의미와 모델 지시가 달라질 수 있으므로 `high`로 둡니다.

## 발표용 한 줄 요약

우리 탐지엔진의 위험도는 “얼마나 위험한 단어가 들어갔는가”가 아니라, **tools.json 메타데이터가 모델을 얼마나 강하게 오염시키고, 그 결과가 민감정보 탈취나 고권한 행동으로 이어질 수 있는가**를 기준으로 정했다.

## 한계와 개선 방향

- 현재 기준은 CVSS처럼 정량 점수화된 표준이 아니라 프로젝트 목적에 맞춘 휴리스틱입니다.
- `severity`와 `confidence`는 분리되어 있으므로, 위험도가 높아도 confidence가 낮으면 추가 검토가 필요합니다.
- `info` 단계는 모델에는 존재하지만 현재 리포트에서는 충분히 활용하지 않습니다.
- 향후에는 `impact`, `exploitability`, `evidence_quality`를 내부 점수로 분리한 뒤 severity를 계산하는 방식으로 개선할 수 있습니다.
- MCP03에 집중하려면 MCP01, MCP04, MCP05 성격의 신호는 독립 취약점이라기보다 MCP03의 impact signal로 해석하는 것이 더 일관적입니다.
